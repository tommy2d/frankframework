# Draft public issue

> Concept only, not for upstream. The implementation it offers is the rest of this branch
> (`fix/browsejdbctable-default-deny`). Drop this commit before opening the upstream PR.

**Title:** `browseJdbcTable.permission.rules` ships as `* * allow`, so every table is browsable by default

**Labels to request:** Security

---

### What happens

`BrowseJdbcTable.readAllowed` is written for default deny:

```java
if (StringUtils.isBlank(JDBC_PERMISSION_RULES)) {
    log.debug("No JDBC table permissions are defined, default deny");
    return false;
}
```

The shipped properties file does the opposite. `core/src/main/resources/AppConstants.properties:830`:

```properties
browseJdbcTable.permission.rules=* * allow
```

That rule matches every table (`*`) for every role (`*`), so the blank check is never reached and
`readAllowed` returns true for anything. The endpoint itself is open to three roles
(`BrowseJdbcTable.java:93`): `IbisDataAdmin`, `IbisAdmin`, `IbisTester`.

### Why the reach is wider than one table

`where` and `order` are placed into the generated SQL verbatim. `browseJdbcTableExecuteREQ`
XML-encodes `where` for the XML, and `BrowseJdbcTableExecute.xsl` then emits both with
`<xsl:value-of>` straight into the query text (lines 20-82). So the `WHERE` field accepts a
subselect, and the table named in the request stops being the limit of what a request can read.

This also makes the console inconsistent with itself. Running a free query is restricted to one
role (`ExecuteJdbcQuery.java:84` and the console controller at `:55`, both `IbisTester` only), while
browsing, which with the shipped default reaches the same data, is open to `IbisDataAdmin` and
`IbisAdmin` as well.

### Why it matters

`SECURITY.md` lists the features that are off by default and names the FileViewer among them. Table
browsing is not in that list, and its shipped default is wide open, so a deployment that grants
`IbisDataAdmin` to an operator for queue and adapter work also grants read access to every table in
every configured datasource. In healthcare that is the patient data itself, not just framework
tables.

### Suggested fix

Ship the property empty, which the existing blank check already treats as deny, and let a
deployment name what it wants browsable:

```properties
browseJdbcTable.permission.rules=
```

The attached branch does that, plus:

* reads the rules per request instead of once per JVM in a `static final`, so a deployment can
  change them without a restart and the behaviour is testable;
* `BREAKING.md` under 10.4 and a `SECURITY.md` bullet, following the same shape as the log viewer
  change in #12077;
* three tests in `TestBrowseJdbcTable`: nothing is browsable with no rules, only a table named in
  the rules is browsable, and a rule for a role the caller does not hold does not grant access.

Existing tests keep the old behaviour by overriding the property in `core/src/test/resources/AppConstants.properties`,
the same way `FileViewerServlet.permission.rules` is already overridden there.

### Not in this ticket

The `where` interpolation is the feature working as designed, so this ticket does not propose
changing it. Narrowing the endpoint roles to match `ExecuteJdbcQuery` would be a second behaviour
change and belongs in its own ticket if you want it.

One further consequence of the wide default was reported separately by email rather than here.
