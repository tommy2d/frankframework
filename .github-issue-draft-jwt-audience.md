**Title:** ApiListener cannot reliably require a JWT audience

**Labels to request:** Security

---

### What happens

`JwtValidator.init` pins the algorithm to RS256 and, when `requiredIssuer` is set, installs a
claims verifier that checks `iss`:

```java
JWSAlgorithm expectedJWSAlg = JWSAlgorithm.RS256;
...
if (StringUtils.isNotEmpty(requiredIssuer)) {
    DefaultJWTClaimsVerifier<C> verifier = new DefaultJWTClaimsVerifier<>() {
        @Override
        public void verify(JWTClaimsSet claimsSet, C context) throws BadJWTException {
            super.verify(claimsSet, context);
            String issuer = claimsSet.getIssuer();
            if (!requiredIssuer.equals(issuer)) {
                throw new BadJWTException("illegal issuer [" + issuer + "], must be [" + requiredIssuer + "]");
            }
        }
    };
    getJwtProcessor().setJWTClaimsSetVerifier(verifier);
}
```

`aud` is never verified, and there is no attribute for it. `ApiListener` offers `requiredIssuer`,
`requiredClaims`, `exactMatchClaims`, `anyMatchClaims`, `roleClaim` and `principalNameClaim`, but
nothing audience-specific, and the nimbus verifier is constructed without an accepted audience.

### The workaround does not work for the usual shape of `aud`

`exactMatchClaims="aud=myapi"` looks like the answer. It compares against:

```java
private String getClaimAsString(String claim) {
    Object value = claimsSet.get(claim);
    if (value == null) {
        return "";
    }
    return String.valueOf(value);
}
```

That works while the token carries one audience, because `JWTClaimsSet.toJSONObject()` writes a
single-element `aud` as a plain string. It stops working as soon as the issuer adds a second
audience: the claim is then a list, `String.valueOf` gives `[myapi, other]`, and a deployment would
have to write `aud=[myapi, other]` to match, which is undocumented and breaks whenever that list
changes.

`JwtSecurityHandler` already documents this, at the top of the same class:

```java
// JWTClaimNames#AUDIENCE claim may be a String or List<String>. Others are either a String or Long (epoch date)
```

and `isUserInRole` in that class handles both shapes. Only the claim-matching path flattens with
`String.valueOf`.

### Why it matters

Without an audience check, an `ApiListener` accepts any valid token from the configured issuer,
including tokens that issuer minted for a different service. Where one IdP serves several APIs, those
APIs end up inside each other's trust boundary, and `requiredIssuer` cannot separate them because
the issuer is the same.

### Suggested fix

Add a `requiredAudience` attribute and pass it to nimbus, which implements the string-or-array
semantics already:

```java
new DefaultJWTClaimsVerifier<>(requiredAudience, null, null)
```

Separately, making `getClaimAsString` list-aware would fix `exactMatchClaims` and `anyMatchClaims`
for every multi-valued claim, not only `aud`.

Happy to send a patch for either or both.
